#+title: 10.10 Build and Test Ownership

* Command ownership

=gerbil build= owns library compilation through the package's existing runtime
Make specification. =gerbil test= owns suite import, Case execution and Harness
results. Ordinary test modules declare suites and fixtures; they do not start a
second package test run. Integration tests of the compiler/process boundary may
exercise that boundary explicitly; this is not the ordinary suite dispatcher.

The retired =unit-tests.ss= dispatcher and the locally patched/rebuilt =gxtest=
are removed. No replacement test engine or Builder is introduced.

=dev/gerbil.pkg= owns optional development dependencies, not another product
library. =build-testing= compiles ASP in its development prefix against the
already selected product library. =test-root= separately requires
=build-library= in the production prefix. There is no =dev/build.ss= forwarding
entry: forwarding the product build while retaining the development
=GERBIL_PATH= duplicates the entire production library and its compiler work.
Tests use the production library first and the development dependency library
second; development preparation does not republish production modules.

The ordinary CLI calls the demand's =.run= once. Core's existing execution
boundary prepares and authenticates support before starting the Harness and
checks currentness again on release. A separate =.compile= operation is for
explicit preparation requests; calling it before =.run= repeats the full
preparation and admission boundary without adding another requested operation.

Gerbil owns import resolution through its configured library paths. The test
projector uses =core-import-module= without replacing the expander's importer,
rewriting symbolic imports to filenames, or classifying installed products by
suffix or prefix. It observes actual imported context paths. Only contexts
matching the admitted package source contribute support targets to =std/make=;
other imported contexts remain dependencies, not test compilation requests.
Production changes require =gerbil build=. Observation does not prove compiler
correctness. Suite, support and configuration mutation controls remain separate.

Ordinary Make completion uses =building/products.ss= for the selected product
inventory and per-unit recovery. Publication/issuance remains in
=building/artifacts.ss= and uses that same inventory implementation. The build
projection resolves its effectful issuance functions through the existing
=module-entry-action= only on explicit =.compile= / =.process= demand. This
separates dependencies, not authority checks: currentness before and after the
callback, output validation and signing still execute at their existing gates.

* Published authoring entry points

Standalone authoring front ends are declared by the existing module source
publication in =modules/module-authoring/source-registry.ss=. The production
build projects those SourceRef values by their entrypoint role and lets
=package-library-spec= / Gerbil derive their import closure. Module interfaces
retain their ordinary roots. Tests do not maintain another list of production
helpers, compile a missing public API into a private test prefix, or substitute
source imports for installed libraries. Missing declared sources still fail.
The removed Testing Module is not a maintained integration directory; the test
interface belongs to =init.exports.tests=.

The large =use-module= transformer retains the same ordered =syntax-case=
clauses under Gerbil's =begin-annotation @no-optimize-syntax-case=. The installed
compiler's =optimize-ann.ss= recognizes this tag and compiles the original
recognizer instead of recursively optimizing its decision tree. It does not
remove syntax checks, Type/Contract checks, source locations or runtime checks.
The annotation is local to this transformer; Make settings and compiler sources
remain unchanged. Qualify with =just build= and =just test-file
t/agent-sandbox-profile-user-interface-test.ss=, followed by =just test-root=.

* Native process completion and build completion

The package command's deadline includes import/expansion, selected-graph
admission, Make, final currentness and normal process teardown. A returned
=std/make= call or =BUILD-STAGE main return= is not successful package acceptance:
the owning command must also exit normally. In particular, dynamic library
unloading after Scheme has returned can consume the remaining deadline.
Do not bypass normal cleanup or approve an interrupted producer's outputs.

Gerbil's =ProcessError= exposes the native wait status. Interpret it with the
installed runtime's =process-exit-code=, rather than calling the raw integer a
shell exit code. Keep the watchdog's own =--verbose= signal report so deadline
termination can be distinguished from an external signal. A signal alone is
not evidence of heap exhaustion or of a POO retained-object leak.

Reproduce through =GERBIL_BUILD_VERBOSE=2 just build-library=, then =just
test-root=. The existing verbosity reports source projection, currentness and
Make separately; Just must not overwrite an explicitly requested verbosity.
Keep process samples and failed execution logs in ignored qualification output.
Sampling must distinguish dynamic-loader allocation/teardown from Scheme GC,
shared loaded code from receiver-owned data, and the parent from compiler
children. No Make scheduler, process-exit shortcut or cache protocol is added.

* External selection and resource policy

=init.exports.tests= publishes the official Harness input spec: a list of test
file paths, consumed by the installed =gerbil test=. It is not a package
manifest, a Make target list, or a replacement TestSuite format.
Ordinary =t/= discovery is the installed tool's default non-recursive directory
operation. Explicit =t/...= requests its recursive mode. There is no product
=dev/tests.ss=, private exclusion table, per-file executor or second Harness.
The retired =tests.for-directory= API and its recursive scanner are removed.

=just test-root= passes =t= or the supplied native arguments to that tool once.
Just owns the pre-import heap and aggregate process fence; existing Case policies
retain their semantic budgets. Focused =just test-file= keeps its 120-second
fence. Whole-suite execution does not claim the former runner's independent
per-file deadlines. No success or admission result is cached.

Build and qualification-input preparation are explicit, independent operations.
CI and the complete repository aggregate prepare them once; focused native tests
do not start Make, another controller, or provider-package preparation. Module
publications and actual domain admission retain their own currentness and
source diagnostics. A generic test-launch receipt cannot replace those checks.
Actual independent-process qualifications still use Ops and the existing Fixture
boundary, including preservation of both original errors on failed cleanup.

Reproduce the bounded migration before running the ordinary directory:

#+begin_src sh
just test-core-file t/testing-script-test.ss
just test-core-file t/init-test-input-test.ss
just test-core-file t/gitea-postgresql-publication-test.ss
just test-root t/agent-sandbox-profile-user-interface-test.ss t/sandbox-profile-poo-type-contract-test.ss
# Repeat the same command in a new process without changing source or outputs.
just test-root t/agent-sandbox-profile-user-interface-test.ss t/sandbox-profile-poo-type-contract-test.ss
just test-root
#+end_src

Record prerequisite/build wall time separately from =TEST-FILE-SECONDS= and
whole-invocation wall time. A new process over existing native outputs is not a
clean compilation experiment. =TEST-FILE-OK= is controller progress only:
acceptance still requires the original per-file =MODULE-OK=, =HARNESS-OK= and
final =OK=, with no Harness error markers. Raw benchmark/failure transcripts
remain local artifacts, not Org content.

** Remaining acceptance boundary: controller-owned expansion

Small passing runtime selections do not qualify an unbounded persistent
controller. Previously, =module-test-source-spec= in
=module-system/source/build.ss= called the official =core-import-module= for
every requesting Suite to discover support. In the installed Gerbil,
=gerbil/expander/module.ss= registers the path and module identity in
=__module-registry=; the module context retains both expanded code and the
delayed evaluator. A fresh top context does not create a fresh module registry.
Consequently, removing process startup without changing compiler-context
ownership can accumulate all previously expanded test bodies in the controller.
This is distinct from POO's ordinary receiver caches and from a Make DAG.

The candidate now uses the official reader and complete module expansion for
the requesting Suite in an invocation-owned analysis context. It does not
register that context, retain expanded runtime code, or install its delayed
evaluator. Imported dependencies still use the official importer. Expansion
includes macro-generated and phase-shifted imports; Suite runtime statements
must not execute during support discovery. A fresh demand re-analyzes the
current Suite source; an old demand must reject changed source. This context
is private analysis data, never a substitute for an authenticated publication.
Macros may have compile-time effects or deliberately retain contexts; this
change does not prove arbitrary macro memory use bounded.

The persistent-controller migration is not yet accepted for the complete
regression. Reproduce with the ordinary =just test-root=; retain the failed
transcript and use explicit paths from its failing prefix for bounded follow-up.
Do not weaken the heap cap, evict native registry entries, strip module code or
add a shadow import registry. The next production change must close support
discovery/expansion ownership through the existing build/test publication
boundary, while preserving its original issued dependencies and currentness.
Controller heap/stack exhaustion fails immediately; it must not be counted as
many independent failing child suites. A child's ordinary nonzero result still
retains its full diagnostic and allows the next independent file to run.

=dev/tests.ss= is a thin CLI consumer of =agentic-ai-lab.init.exports.tests=.
It asks the existing =.for-files= method for a bounded demand, refines that
demand's execution policy and explicitly calls =.run=. It does not construct
another =TestingScript.= or select a compiler. The same entry serves ordinary
focused tests and the existing long-budget diagnostic command. Core owns
selection, demand-scoped support preparation, runtime issuance and execution.
Its command remains the installed =gerbil test=, with the original pre-import
heap fence and watchdog. Core's source guard and exact
=MODULE-OK=/=HARNESS-OK=/=OK= result admission remain in force, including failure
markers even when a tool exits zero. This is outside the test Case, not a Case
launching another test Harness.

The public owner is the same init export that publishes =std-make-spec=:

#+begin_src scheme
(def tests
  (.call (.get agentic-ai-lab.init.exports tests) .for-files
    '("t/gerbil-runtime-import-test.ss")))
;; No process is started by obtaining this object.
(.call tests .run)
#+end_src

The legacy =t/= exclusions remain plain data in the CLI consumer until the
suites move to module-owned directories. They are applied by the init-owned
directory projection, not by ASP or another product scanner. The retired
=dev/test-file.ss=, =dev/test-files.ss= and =dev/testing-profiles.ss= do not
remain as forwarding entrypoints. The package-file diagnostic uses this same
publication instead of constructing a separate qualification Script.

** Syntax binding is a separate obligation

=init.exports.tests= already publishes selection, preparation and execution.
It does not yet inject the lexical =yuanxu-test-case= or Fixture macro bindings
into ordinary test sources. The existing macros expand hygienically to runtime
=std/test= TestCases and retain their Case policy. Automatic binding must join
the existing compiler-source role preparation on both reading and compilation;
it must preserve original locations and explicit non-default preludes. Adding
an eval-time import to a CLI, changing the global package prelude, or declaring
an alias named =yuanxu-test= would not close that obligation. No such replacement
is introduced here. Loading an init export must remain inert. A proposed
test-only package/prelude was withdrawn: neither =t/gerbil.pkg= nor a separate
testing language is required by the official Harness. Explicit runtime test
macro imports remain until the existing role preparation can supply them
without changing the Harness interface.

The product consumer migration is exercised through default =just test-file=:
the runtime-import control passes with an empty support spec. The build-boundary
regression passes through the init-owned demand, including inert =tests= access
and distinct cross-package entries. Its first run compiles three support units;
a second Just process reports =issuer-reused=#t=, =make-seconds=0= and
=compile-count=0=. Both complete with the required runtime Harness markers and
no failure markers. This demonstrates reuse of the existing issuance owner,
not a new cache or a cached test verdict. Automatic lexical macro injection and
full CI closure are not established by these runs.

Ordinary =just test-file= does not prepare Provider artifacts or Nix executables.
The full package and explicit Nix qualification prepare those inputs separately.
The Nix environment transport runs once for the full package, not on every file.
Core module-system qualifications retain their existing signed support-build
entry; this change does not replace that protocol with an unissued Make call.

** Runtime startup diagnosis

The unchanged five-second refusal was reproduced with failure-only Darwin stack
sampling. In that one-second sample, 56 of 95 main-thread samples were under
=___dynamic_load=/=dlopen=; 53 included dyld debugger-image notification, with
synchronous Mach-message waits visible. Only two samples were in the GC branch.
This is a sampled startup interval, not a measurement of the complete run or
proof that the host is the sole cause. It does establish that this failure
occurs while loading runtime images before Harness output, rather than while
compiling a test Case. The sampling time cannot earn a pass: the watchdog has
already rejected the process before collecting its stack.

The outer qualification process and the runtime test child must be attributed
separately. Removing the runtime import of the build entry addresses one actual
phase dependency; it does not establish that the child now meets the progress
gate. A passing build, a parsed workflow and a focused source regression must
not be reported as a passing AOT runtime or complete CI.

Before the module-publication migration, the bounded runtime AOT build exited zero
with no compile jobs on the hot run. The default
=just test-file t/build-projection-observability-test.ss= also exits zero with
=MODULE-OK=, =HARNESS-OK= and final =OK=, without failure markers. Workflow lint
and whitespace checks pass. These results qualify phase separation and runtime
Make reuse; the failed child startup, Nix build and scale results above remain
open.

* Publication is the declaration; spec is a projection

The compiler entry is public =std/make.make=; clean and CLI dispatch stay with
the runtime =defbuild-script= path. Core projects selected ownership and source
observations into that spec, but must not replicate dependency timestamps,
worker scheduling or private Make internals. The latest discovery correction
preserves runtime compiled-library imports instead of rewriting their internal
dependencies into test source targets. The real Gitea/PostgreSQL control then
compiled two private support units and passed all eleven Cases. Empty support
also avoids importing the signing runtime, verified with the SDK's actual
=list-modules= and a nonempty positive control. See Core 13.18 for the measured
source snapshots and remaining qualification boundaries.

** Bounded file-demand measurements

The 2026-10-26 local source snapshot exposed two avoidable dependencies:
=.cc= arguments acquired the selected graph eagerly, and SDK-only progress /
role metadata utilities inherited the package POO prelude. Runtime lazy slots
now defer graph acquisition; those two utility modules explicitly select
=:gerbil/core=. Export-name calculation lives with role metadata, rather than
requiring the selection parser merely to obtain a symbol.

The same minimal SDK test, through default Core =just test-file=, passed with
=MODULE-OK=, =HARNESS-OK= and final =OK=. After the lazy-slot change its wall
time was 55.71 seconds; after the utility import changes it was 30.13 seconds,
then 24.57 seconds in a separate process on unchanged sources. The last two
selection deltas were about five milliseconds, with zero linker, reader
bootstrap and selected-graph calls. These are local wall measurements, not a
controlled host benchmark or a claim that startup meets the 5--7 second goal.
The minimal test has no support compilation, so it cannot establish signed
artifact reuse or full product qualification.

The runtime module runtime cache is process-local. A capability probe measured
an already-loaded module at 0.000083 seconds, while loading its expansion
interface still incurred substantial work. Replacing runtime imports wholesale
with =load-module= would lose lexical/expansion responsibilities; it is not a
justified fix for fresh-process startup. Remaining startup cost must be
attributed separately from selected business-role work.

The test of discovery mechanics no longer invokes the complete selected test
group from inside one TestCase. That integration demand belongs to the external
=just test-selected-modules= gate, retained in CI. This relocates its original
coverage; it does not demonstrate that the full group's cold compilation cost
has disappeared.

Core's follow-up preparation control traced 23 support units to an unnecessarily
broad Fixture owner. Generic directory resources now live only in
=core/t/qualification/testing/directory.ss=; service-publication support imports
them and consumers bind private support through runtime relative imports. The
same default regression now passes with two outer support units. Cold runtime
Make took 48.375 seconds; a fresh-process hot run restored the approved outputs
with zero outer compile jobs. Whole-command times were 290.03 and 101.19 seconds,
including the integration Cases' deliberate fresh builds and refusal controls.
This closes that cold preparation failure, not the remaining startup latency,
Nix qualification, scale gate or full CI. Detailed receipts and boundaries are
in [[file:../../core/docs/10-19-design/13-module-loading/13.18-guarded-test-precompilation.org][Core 13.18]].

** Runtime publication example

The Context/Temporal qualification declares its exports in a Scheme
module. =spec= contains only the resulting Harness input, never a second list
of what the qualification does:

#+begin_src scheme
(def tests
  (.call (.get agentic-ai-lab.init.exports tests) .for-files
    '("t/qualification/context-temporal/interface.ss")))
(.call tests .compile) ; signed preparation only, no Harness or TestCase
(.call tests .run)     ; independent currentness, hot preparation, gerbil test
#+end_src

The original 99-Case admission, 45-second qualification and five-second genuine
progress watchdog remain. CI prepares the published module separately under
the existing 120-second compilation cap. Compilation and execution use the
same runtime dependency closure and approval owner; no extra Builder or cache
protocol is introduced. The old startup/scale/Nix failures remain failures
until their new-path executions pass.

* Context build ownership convergence, 2026-10-26

=agentic-ai-lab.init.exports.std-make-spec= is the production build owner.
=build-spec.ss= supplies the retained runtime-library import closure and existing
platform options to that owner. The duplicate =build-modules.ss= and
=dev/package.ss= catalogs and the =dev/build.ss= forwarding entry are removed.
The development prefix builds dependencies only. Bootstrap initializes a missing Core checkout without resetting an
existing revision or local work.

The 39 specialized Context/Temporal build aliases are removed. Executable
qualifications and runnable Org instructions now consume =build-library= or
=build-test <path>=. The latter asks =init.exports.tests.for-files= through
=dev/tests.ss compile=; Core owns support discovery, source admission, Make and
artifact recovery. The explicit Actor AOT executable consumes a driver and does
not publish a second module catalog. The numbered-object cleanup script is also
removed. Historical JSON receipts keep their original commands and verdicts.

The C artifact materializer uses the selected =gerbil build= frontend, then
=gerbil env= for SDK static-dependency resolution. Both steps retain the runtime
package environment; Python does not invent module order or dependency paths.
The successful artifact materializes 328 SDK-emitted user units. A plain C
consumer loads that artifact and exercises actual SDK setup/cleanup, descriptor
projection, result release, foreign-thread refusal, control-lane refusal,
trailing-datum rejection, absent-service refusal and terminal close/reopen.
No setup/cleanup mocks, forced process exit or Rust binding is involved.

#+begin_src sh
just build-library
GERBIL_TEST_MAX_HEAP=2G just build-test t/context-service-test.ss
GERBIL_TEST_MAX_HEAP=2G just test-context-service /private/tmp/NEW-context.sqlite
just build-semantic-runtime /private/tmp/context-semantic/libsemantic.dylib
just test-semantic-c /private/tmp/context-semantic/libsemantic.dylib
#+end_src

The current build-boundary regression and runtime Context service probe pass
with =MODULE-OK=, =HARNESS-OK= and final =OK=. The service retains single-terminal,
historical retry, substitution refusal, proactive revocation, unaffected
consumers, no revival and joined shutdown controls under 2 GiB/150 seconds.
Focused compilation reports =issuer-reused=#t=, =compile-count=0=; that is reuse
of issued compilation, not a cached test verdict. The Python descriptor contract
also passes against the packaged artifact after building the existing CFFI shim.

The standalone C probe installs no live Context. Its VM/ABI result and the
Scheme probe's active Context/Session result are separate evidence. Complete
60-case replay, performance, distributed-runtime qualification and exact-head CI
are not established by these checks. Failed package-environment attempts and
the missing Python CFFI attempt remain local evidence, distinct from passes.
See [[file:10.06-poo-module-system/agentic-ai-context/31-build-unification-results.json][the source-bound structured receipt]]. Raw build logs, binaries and journals
remain local artifacts.
