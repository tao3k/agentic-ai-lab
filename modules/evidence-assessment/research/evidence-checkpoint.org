#+title: Evidence Checkpoint and Recovery Contract
#+status: Core design; executable relational kernel; host integration remains explicit

* Problem and ownership

A progress counter cannot explain which work survives a restart or source
change. A single CURRENT/STALE bit discards independent support and encourages
whole-campaign reruns. A read cursor cannot establish native completion.
Treating these as interchangeable is an architectural error, not an Agent
instruction problem.

Use the existing registered Evidence sources, Session transactions, immutable
Trajectory prefix and support graph. There is one evidence history, not a new
checkpoint database. The Library derives state; a host observes files/processes
and owns persistence; downstream Scheme declares requirements and contracts.
The Library never runs build commands or authorizes native execution.

* Configurable reasoning support, not a Harness state machine

The supplied constructor is an optional reusable declaration, not a mandatory
checkpoint owner or closed policy vocabulary. The existing registry selects
Scheme sources and constructors. Consumers can replace the declaration or
compose their own relations using ordinary Session source updates; no Python
branch, new flag, host callback or Library rebuild is needed for domain facts.
The exported =evidence-checkpoint-fragment= is composed with ordinary =include=;
the default constructor is only a convenience. Extensions do not rewrite rule
text or fork the checkpoint implementation.

Requirements, dependency edges, contract identities, current input bindings,
accepted completion outcomes and material obligations are supplied relations.
The current contract relation is an accepted set, not a forced single version;
independent compatible checkers may support the same requirement. An immutable
receipt ID still names exactly one host-verified receipt, not a union of claims.
There is no fixed milestone list, fixed graph, fixed order, default PASS token,
required number of attempts or predetermined path. =completed_outcome= can name
a successfully decoded negative control under its own checker contract; that
does not turn the failing runtime into a native success. Host verification and
the receipt's actual qualification scope remain independent premises.

Consumers may expose additional applicability or uncertainty relations, use
alternative registered constructors, choose arbitrary query/scope, and revisit
old evidence intentionally. These are open extensions, not options selected
from an exhaustive Library menu. Checkpoint evidence amplifies the model's
ability to reason with retained work; it neither chooses nor prohibits ideas.

The constraints are on truth claims: an unverified label cannot become evidence,
an incomplete read cannot become a completed test, and a projection cannot
grant execution authority. They are not constraints on model exploration.

The core engine stays below these declarations: it owns evaluation, dependency
maintenance, transactional publication, cancellation and observable provenance.
The provided checkpoint declaration is a reusable policy component, not a new
engine primitive. Downstream applications can register another constructor or
derive another view without changing the engine. A universal fixed recovery
state machine would reverse this layering and is explicitly not the design.

* Evidence exchange composition

The same checkpoint module exports =evidence-checkpoint-exchange-fragment=.
It includes the existing closure kernel, rather than reimplementing receipt
admission in a host or a downstream navigator. =checkpoint_claim= maps a
caller-owned claim to a requirement, qualification scope and declaration source;
=checkpoint_source= binds paths/digests, and =checkpoint_receipt_source= binds
each receipt to its retained report. The existing constructor accepts these
optional relations; no additional command or navigation interface is required.

=checkpoint_observation= projects applicable support, historical-only support,
unclosed requirements and recorded noncompletion. =checkpoint_dependency=
exposes evidence references, not a prescribed execution order.
=checkpoint_reason= keeps each reason bound to its own receipt and origin;
an obsolete receipt's mismatch must not be attached to a newer valid receipt.
Downstream Scheme maps these rows into its existing Clue/factor/link vocabulary.
Python observes and transports; it does not decide applicability or completion.

A component's qualified report is not a receipt for a dependent source repair
or native test. Reading every returned unit changes acknowledgments, not any
requirement's support. Cleaned binaries can prevent reuse without erasing
historical or applicable evidence. A failed receipt remains counterevidence,
not an absent event. Qualification scopes remain caller-declared and visible.

=CheckpointProjection.qnt= checks partial support and seven falsifying
mutations. =EvidenceCheckpoint.lean= states the general missing-target,
component/goal separation, changed-parent and cleanup preservation properties.
Real Session tests bind the projection to the existing relational kernel and
exercise first reads and new-process checkpoint continuation. These checks
are not an implementation-refinement proof or native SMP acceptance.

* Four distinct cuts

| Cut | Meaning | Never establishes |
|-----+---------+-------------------|
| Read acknowledgement | Declared query, completely displayed Clue units and expansion references | Test completion, applicability or execution authority |
| Trajectory prefix | Exact committed event prefix and its source/support bindings | Unobserved events or hidden reasoning |
| Evidence checkpoint | Receipt-backed completion and present applicability of requirements | Availability of deleted binaries or process teardown |
| Execution observation | Host-attested exit, quiescence and material availability | Validity of a receipt whose premises changed |

These cuts reference each other by identity; none is coerced into another.
A task showing 6/12 is a projection of declared requirements with supporting
receipts, not the identity of an execution directory. Requirements need not be
numbered, fixed in number or totally ordered.

** Query restoration is not answer replay

A real SMP Grok continuation exposed a missing contract: its first call supplied
only the prior read token, but the downstream CLI demanded another anchor or
query. The earlier tests always supplied both. A token that retains only shown
units cannot reconstruct the caller's selector from its digest.

The existing ClueExchange now retains the inert query declaration inside its
content-bound checkpoint: questions, selector sources/constructor, bindings and
expansion/presentation fields. A checkpoint-only read reopens that declaration
through the existing Session and re-evaluates Scheme against current attested
facts. It does not freeze the old resolved claim list. Restored intent is not
restored support. A changed evidence snapshot is rederived, not automatically
treated as a changed reading contract; the rules below define that distinction.

Explicit questions replace the saved query scope. Explicit bindings/expansions
can revise the continued declaration, and a caller-supplied selector remains
caller-owned. Empty supplied fields differ from absent fields. There is no
recommended action, fixed navigation policy or additional execution authority.
Python preserves those distinctions in transport instead of inserting empty
query fields or implementing selection. A checkpoint missing its declaration
cannot silently invent an anchor or report that matching evidence is absent;
the caller must provide query intent again. Historical evidence is unchanged.

=ClueQueryResume.qnt= checks restoration, current-fact re-evaluation, missing
declaration handling, caller override, history and authority boundaries; six
mutations expose their expected counterexamples. =AnchoredEvidenceSlice.lean=
adds general Option-query restoration/override composition and current-answer
laws. Native integration controls exercise a new owner, changed facts, custom
Scheme selection, arbitrary new scope, altered bytes and missing declarations.
These are algorithm/protocol controls, not a proof of Rust source refinement or
an assertion that a probabilistic Agent always chooses the interface first.

The integrated native selection subsequently passed all 97 tests. Downstream
passed 46 progressive-query tests and 1,740 full-framework cases with no
failures (40 engine-dependent skips passed separately with the actual seal).
In a real Grok SMP continuation the first three tool calls were framework
queries; calls two and three omitted bindings and stayed incremental. A fresh
CLI process consumed the resulting token alone: 161 rows retained, no repeated
families, complete presentation, no execution authority. The initial failed
checkpoint-only call and corrected test assumptions remain recorded downstream.
This closes the demonstrated query-transport gap, not native SMP qualification,
physical-machine reboot testing or a universal Agent-efficiency claim.

* Immutable support and current projection

** Complete inventories and raw command observations

=closed_support(receipt)= is now derived, not supplied by the host. The accepted
=support_declaration= binds requirement, contract, scope, declaration digest,
enumerator/checker identity and the input/command/dependency cardinalities.
=support_witness= independently references the retained enumeration observation.
Scheme requires matching identities and coverage of all declared member tables.
Explicitly witnessed empty inventories are valid; a missing witness or missing
member is not an empty-inventory success.

Cardinality is not a proof of roster identity. The host checks exact retained
member maps and original step content against the immutable observation prefix;
same-sized input substitution is rejected. Source custody, admitted enumerator
implementation and complete enumeration within its declared scope remain host
premises. Neither a digest nor QNT/Lean discovers undeclared external semantics.

=required_binding(requirement, contract, key)= declares a required input for
that checker contract, not a union across independently accepted checkers. =binding=
contains its recorded digest and =current_binding= contains observed bytes.
The Library derives =binding_gap(receipt, key)= for missing, changed or
ambiguous input bindings; missing bindings are not a successful empty check.
Dependency invalidations retain their original receipt and reason. Adding an
unrelated source key cannot invalidate an independent receipt.

=command(receipt, command, expected_exit)= declares a command obligation;
=command_observation= supplies actual exit, timeout, reaping and group-quiescence
observations. Scheme, not Python, checks the expected exit and all three
completion conditions. A missing observation stays unresolved. An intentionally
nonzero expected exit is configurable and does not authorize a timed-out child.
Native host facts and their immutable custody remain premises of this rule.

** Reading contract versus evidence snapshot

The existing read checkpoint binds both snapshot identity and
=readContractIdentity=: projection declarations, constructor and Library rules.
On a changed snapshot with the same contract, the existing Session rederives
all current scoped facts; the Scheme delta matches full content tuples, not
counts, claim names or a Python cache verdict. Exact unchanged units can remain
acknowledged. Changed/withdrawn units and new counterevidence make their family
visible again. =refresh= describes this comparison; it grants no applicability
or execution authority. Out-of-scope old acknowledgements are historical read
records, not assertions that those units remain current.

Changing the reading contract resets acknowledgements conservatively. An old
checkpoint without that contract cannot reuse acknowledgements across changed
snapshots. Explicit caller queries still own scope. Arbitrary new hypotheses,
selectors and expansions remain legal; this is not a recommended-action API.

** Layering and implementation boundary

Python consumers already call the compiled ASCENT reader and SourceSession;
they must not parse Scheme into Python expressions or implement the rules a
second time. Native compilation owns the general reader, expansion, validation
and evaluator. Registered application declarations remain loadable data, so a
new domain association does not require rebuilding the Library. Compiling all
downstream declarations into ASCENT would invert that configurable boundary.

A Python AST walk over Python implementation imports is a different concern:
it identifies the implementation closure whose bytes are sealed. It is not a
Scheme parser. Removing it without replacing the custody mechanism would lose
dependency coverage rather than eliminate duplicated inference.

This revision is qualified upstream before downstream installation. Upstream
protocol checks do not admit SMP. A downstream integration must use a frozen,
identified Library candidate and retain its actual source/receipt identity;
the installed older Library is not silently patched with loose source files.

returned: a status without its origin was not adequate evidence. The transport
now preserves that existing relation. Another full-framework regression found
that registration bound every source in the registry, including an unrelated

adding path exceptions in each consumer. The registry file itself remains an

does not claim a minimal semantic manifest dependency or lazy filesystem I/O.

An execution terminal is an immutable committed tail. The host transaction
rejects append-after-terminal without damaging the prior prefix. Permanent
closure differs from a transient CAS conflict and must not enter a retry loop.
This is journal integrity, not a fixed domain workflow or an Agent action ban:
a new execution remains possible under a new identity. The same obligation is
checked in =EvidenceCheckpoint.qnt= and =EvidenceCheckpoint.lean=.

*** Configurable work witnesses in the existing checkpoint Session

The registered checkpoint Library also exports =evidence-progress-fragment=;
=make-evidence-checkpoint= composes it without a second query endpoint. A
downstream constructor may include the same fragment through its existing
component registry. No task names, GC operation names, host CPU counts, timeout
constants or investigation directions are built into the rules.

| Input | Host-observed or caller-declared meaning |
|-------+-----------------------------------------|
| =progress_contract(scope, actor, epoch, kind, source)= | Accepted meaning and provenance of a work counter |
| =progress_active(scope, actor, epoch)= | Host-established current producer incarnation, not an inherited checkpoint assertion |
| =progress_cursor(scope, actor, epoch, kind, source, value)= | Last retained counter baseline; an explicitly known nonnegative integer |
| =progress_sample(id, scope, actor, epoch, kind, source, value)= | Observed counter with immutable observation identity |
| =progress_attested(id)= / =progress_completed(id)= | Host custody/attribution and completion witnesses; neither is inferred from output volume |

Scheme admits a sample only for the exact active contract, with both witnesses,
nonnegative integer counters and no contradictory payload under its observation
identity. Conflicting active incarnations or cursors cannot renew a watchdog.
The frontier is derived in Scheme, and =progress_advanced= additionally requires
a strict increase over the matching retained cursor. Missing or conflicting
cursors produce an explicit =progress_rejected= reason instead of silently
becoming zero. Typed scalar admission rejects booleans masquerading as integers.

The host collector must bind actor incarnation and source to the owned process
or authenticated child channel. A producer's self-reported PID, busy CPU,
arbitrary increasing heartbeat, GC request or log timestamp is not a completion
witness. Attestation includes stable observation identity across batches; this
is an explicit host premise, not something Datalog proves about arbitrary I/O.
A completed collection plus verified mutator work may be a domain witness, but
the Gambit-specific correspondence has not been established by these generic
rules. Independent actors/kinds keep independent cursors; they are not summed
into a synthetic work counter by the Library.

The existing host inactivity loop renews its monotonic timer only when this
Session returns an advance. It retains the raw batch, cursor before/after and
decision in the existing execution journal. Observation inputs are replaced per
batch: omitted attestation/completion rows cannot inherit a previous batch's
witnesses. A collector may emit just its new batch; it need not replay the
entire execution history. Host bookkeeping counts admitted renewals only to
adapt the existing callback signature; it does not implement the inference.

Recovery retains cursor facts and immutable history, never a live-process claim
or a fresh renewal. A new query owner must obtain current host attribution before
accepting later work. After a cache clear, the existing retained prefix is read
from the checkpoint store, not recreated from missing disposable process files.
A new owned process is a distinct incarnation with its own declared baseline;
it does not reuse old events as work. Recovery does not reopen a terminal run,
authorize a process or turn progress into task success. Physical OS reboot and
application-specific child attribution remain distinct host validation duties.

The finite =ProgressWitness= model checks correct completion and eleven fault
controls, including stale epochs, heartbeats, missing/conflicting cursors and
restoration that invents renewal time. Lean checks the corresponding context,
completion and replay premises under LeanPoo's Guard. Installed Session tests,
actual subprocess inactivity/exit tests, immutable journal writes and fresh-owner
recovery after deletion of disposable run files exercise the connection points.
These are framework qualification, not a native SMP pass or a promise that every
domain already emits a suitable witness.

Each receipt identifies its requirement, checker/contract, complete support
manifest, exact prerequisite receipt identities and outcome. Complete means a
host-admitted declaration of relevant inputs and dependency inventory, not
merely the files an experiment happened to read. A missing or incomplete
manifest is unknown support. Native tests that depend on a runtime include
that runtime's build receipt as a prerequisite: changing runtime code normally
invalidates all tests using it. Independence must be declared and checked,
never assumed in order to avoid tests.

The generic Scheme kernel exposes independent relations:

| Relation | Interpretation |
|----------+----------------|
| =historical_complete(requirement, receipt)= | Verified successful receipt with complete successful prerequisite ancestry |
| =applicable(requirement, receipt)= | Historical completion matches current contract, bindings and dependency inventory |
| =reusable(requirement, receipt)= | Applicable, quiescent and required material currently available |
| =invalidated_by(receipt, origin, reason)= | Traceable direct or transitive support gap |
| =unclosed(requirement)= | No applicable successful receipt in the complete supplied window |
| =material_gap(requirement, receipt, artifact)= | Applicable evidence exists but required bytes are absent |
| =completion_gap(requirement, receipt)= | Applicable evidence exists but parent quiescence is unobserved |

=unclosed= is relative to the supplied finite closed requirement/receipt window,
not a claim that no other evidence exists. A scoped window must contain complete
prerequisite ancestry, or explicitly exposes a gap. Multiple attempts coexist;
a newer failure does not delete an independently applicable older pass. A
withdrawal revokes current support but does not erase historical completion.

Let I be directly unsupported receipts and D the recorded prerequisite graph.
The invalid set is the least fixed point I* = I union dependents(I*).
It is monotone in direct gaps for a fixed closed graph. Rebinding a source or
replacing a registry declaration recomputes the projection transactionally;
invalidation is not a permanent blacklist. SCCs must be qualified as atomic
units, or cyclic receipt ancestry is rejected. Recipe execution does not infer
that a circular set of successful labels proves itself.

* Persistence, publication and recovery

Persist the source/registry/rules identity, exact committed prefix, immutable
receipt references and dependency bindings through the existing store. Commit
receipt plus support atomically before publishing the checkpoint reference.
Compare-and-publish against the observed prefix prevents two owners from
silently overwriting each other's progress. A changed prefix causes refresh,
not a forced action and not historical data loss.

Recovery authenticates the committed prefix, then re-observes current source
bindings and required artifacts. A crash between journal commit and final
receipt publication yields a committed prefix, not a fabricated aggregate PASS.
A reboot does not prove that an unobserved previous child exited successfully.
Missing raw cache leaves durable receipt history intact; unavailable material
is a separate facet. Never repair missing custody by inventing success.

Watchdog state and performance measurements are also distinct: an old timeout
remains a failed attempt; a newly authorized phase has its own real-progress
watchdog. Checkpoint recovery cannot silently reset a cumulative authorization
budget or charge a readback as a fresh native test.

* Execution consumer boundary

The checkpoint is advisory evidence, not an action list. A host may consume an
applicable receipt through an existing typed artifact capability, or explicitly
requalify an unclosed requirement. It records the originating receipt, current
contract/support and independently observed bytes. It must not mark a skipped
test as freshly executed, copy an old elapsed time into a new run, or promote
a seed compiler into a completed bootstrap.

No Agent hypothesis, expansion, repeat or scope is forbidden by this kernel.
An intentional repeat remains possible under ordinary host authorization.
There is no =next=, ranking, closed menu, hidden keyword router or domain-specific
Python planner. No new flags or checkpoint protocol version are required.
