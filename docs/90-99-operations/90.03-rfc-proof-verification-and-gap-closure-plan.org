This is the execution plan for verifying the active POO module-system RFC
cluster.  It is intentionally separate from the design RFCs.

[[../10-19-design/10.06-poo-module-system/45-11-rfc-formal-model-and-lean-proofs.org][RFC 45-11 — POO Module System Formal Model And Lean Proof Obligations]].

shadow prototype system, POO evaluator, fixed-point engine, linearizer, or
fallback object runtime.

The plan does not authorize architecture changes.  A failed proof or runtime
counterexample starts an RFC discussion; architecture changes require explicit
approval before the owning RFC, Lean model, or implementation is changed.

* Objective

For every normative architectural proposition, establish an evidence chain:

1. a stable proposition identity and owning RFC;
2. an explicit mathematical or operational model;
3. a machine-checked theorem where the proposition is formal;
4. a correspondence argument from Scheme/=gerbil-poo= to the model;
5. implementation and runtime evidence;
6. a durable qualification receipt.

* Verification classes

** Formal theorem

Use Lean for:

- identity separation and equality/non-equality properties;
- state-transition safety and impossible transitions;
- trace invariants;
- graph, lineage, fixed-point, and cycle properties;
- admissibility and evidence-construction rules;
- concurrency safety when the scheduler assumptions are explicit.

Every theorem must build under the pinned local Lean toolchain and pass AXLE
with no failed declarations, errors, warnings, =sorry=, new axioms, or unsafe
declarations.

** Semantic correspondence

Use source/API evidence plus focused Gerbil witnesses for:

- hygienic macro expansion;
- exact =gerbil-poo= constructors and operators;
- runtime root and lineage identity;
- demand-cell and continuation behavior;
- POO-native capability and refinement semantics.

A correspondence item is blocked, not guessed, while an exact =gerbil-poo=
symbol remains =semantic-required= or merely =symbol-located=.

** Implementation qualification

Use property, model-based, negative, and integration tests for:

- macro/parser behavior;
- concurrency and cancellation races;
- bounded observability and sink failures;
- runtime handoff and reinjection;
- provider search resolution;
- installed dependency and artifact identity.

** Operational evidence

Use durable receipts for:

- resolved dependency revision;
- proof source and theorem-set digest;
- installed artifact identity;
- runtime observation identity;
- qualification policy identity;
- freshness, revocation, and supersession.

* Failure classification and RFC return protocol

Every failed obligation is classified as exactly one primary kind:

| Failure kind | Meaning | Immediate action |
|---+---+---|
| =model-gap= | required entity or relation cannot be expressed | add a proposed type/relation; do not alter RFC yet |
| =false-theorem= | RFC proposition has a formal counterexample | freeze dependent tranche and start RFC discussion |
| =missing-premise= | proposition is valid only with an unstated assumption | present the minimal premise for approval |
| =correspondence-gap= | model is coherent but Scheme/=gerbil-poo= mapping is absent | gather exact API/runtime evidence |
| =implementation-violation= | implementation contradicts an accepted model | repair implementation after scope confirmation |
| =evidence-gap= | behavior may be correct but durable proof is insufficient | strengthen receipt/test; do not claim qualification |
| =tooling-gap= | verifier cannot currently express or execute the obligation | isolate tooling work from architecture semantics |

Required counterexample record:

- obligation id and owning RFC heading;
- exact proposition and premises;
- smallest Lean term, trace, graph, or runtime fixture that fails;
- whether the failure is model, architecture, correspondence,
  implementation, evidence, or tooling;
- downstream obligations invalidated by the failure;
- candidate alternatives and their semantic cost;
- explicit statement that no architecture change has yet been approved.

* Receipt requirements

Each tranche receipt records:

- obligation ids and owning RFC source digests;
- Lean toolchain and aggregate build result;
- theorem names and source digest;
- AXLE environment, request ids, errors, warnings, and failed declarations;
- exact =gerbil-poo= revision and API evidence states;
- focused test commands, counts, and negative-case results;
- installed artifact and runtime identity where applicable;
- unresolved, blocked, and counterexample obligations;
- dependency closure invalidated by any failure.

* Completion criteria

The programme is complete only when:

- every normative proposition has a stable obligation id;
- every obligation is operationally qualified, explicitly not applicable, or
  rejected through an approved RFC change;
- no =blocked=, =counterexample=, or unregistered MUST-level proposition
  remains;
- all Lean modules build without =sorry=, new axioms, unsafe declarations,
  errors, or warnings;
- AXLE independently accepts the declared theorem set;
- Scheme/=gerbil-poo= correspondence is proven for every formal constructor;
- positive and negative runtime gates pass against installed artifacts;
- durable receipts bind the complete source, theorem, dependency, artifact,
  and runtime evidence closure.

Passing Lean alone is never closure.
