Gerbil's native import stores the expanded module body and delayed
evaluation on the Context and registers it by path and identity.
Ordinary library traversal needs its import and prelude edges.
The production compiler can use the same Context and the Reader
authenticates relevant Context identities. A wholesale registry
reset would therefore need a stronger source, phase and nominal
identity proof. Trimming the returned POO Graph or changing only
the source stamps is unlikely to close this observed heap deficit.
This forced-GC diagnostic ran no native Make compilation and is not
a cold-build or throughput result.

The native Context identities rule out re-expansion of those three
primary source modules as the explanation for their compiler-stage
increase. The count alone does not classify the additional Contexts
or bound the entire compiler's memory. The native optimizer can
replace a Context's expanded code while preserving its identity.
An identity comparison therefore establishes reuse but cannot
certify equivalence of expansion state across independent phases.

On the original =nix-contracts.ss= source, a matched native compiler
control varied only the optimizer option. Both processes generated

same source Context. The default optimized action added 193
registered Contexts, of which 192 had =.ssxi.ss= paths and one had
an =.ssi= path. It retained another 120,425,544 live bytes after GC
and replaced the Context's expanded code. Without the optimizer,
the same target added no Contexts and 25,120 live bytes, and the
Context code retained its original identity. The non-optimized run
is a diagnostic, not an artifact-equivalence or runtime result.
The default Make options remain in force.

Package windows read the native Gerbil checkout tree under =gerbil-path=.
The source reader has no reason to initialize the package manager or to
create directories. Installation, checkout placement, pinning, and compiled
library resolution remain Gerbil's responsibilities. Compare any package
root experiment outside the Graph and report its loader IDs separately
from Gerbil Contexts and native Make targets.

The runtime reader uses its own native Context as the root of its
source-authentication closure. The Core source bootstrap retains its
build entry roots. Both use Gerbil's import identities and the same
Context traversal for the shared role languages and value libraries.

An installed Context can remain a Gerbil prerequisite while an explicit
selected source owner has a separate byte obligation for the same Module
ID. The reader retains authenticated owner observations in its existing
currentness guards. The installed Context adds no Make target. Core's
=t/module-reader-tool-context-test.ss= exercises the distinction using a
relocated source checkout: an unrelated edit is allowed, an admitted
owner edit or removal is refused, and the installed prerequisite stays
out of the compiler inputs.

The existing =SourceClosureWork= Lean proof and =ToolOrigin= Quint model
cover previously captured native Context identity and its source obligations.
A root interface that has never been loaded has no captured Context, and a
root-path check alone cannot certify its transitive inputs. Keep eager Context
enrollment until the native import path can authenticate that dependency
closure before its first expansion effect.

Lexical use alone also underestimates enrollment. Scenario does not refer
to its imported =AdapterResult= binding, but Gerbil still loads the
runtime-protocol image while the Reader enrolls Scenario's Context.
Compare fresh builds of Scenario with and without that import in private
prefixes, then replace =runtime-protocol.ssi= after Reader creation. A
separate publication must demand =AdapterResult= through its own role.
The original graph protects the role from the replacement's expansion
effect. Removing the seemingly unused import lets the replacement run
and the role return. Preserve enrollment until the receiving import can
authenticate the actual native Context before expansion.

Observe the build interpreter, the outer =gerbil build= process, and the
action watchdog as distinct processes. Bound each exit using the last
live and first absent or zombie observations, with timestamps around
each process-table read. Attribute parent collection only after the
supervised command has exited. The interpreter can be in synchronous
dyld unload notifications, and the outer CLI can remain alive after the
interpreter exits. Keep the process census separate from the ordinary
aggregate qualification.

Parallel Make and compiler workers can interleave their output on the
same line. The downstream tests share the target reader in
=t/qualification/yuanxu-build-events.ss=. Replay the original transcript
and compare the complete sorted target list, retaining duplicates and
rejecting a missing target. A worker suffix is independent of the target
identity. Keep a failed cold process receipt even when its transcript
contains the expected targets or reports that =main= returned.

An idle refusal before the first native compile line also needs separate
attribution. Compare the last completed specification or source admission
span with the progress received by Ops. Native compile records can be
absent throughout specification preparation. Building reports the successful
specification and owner check through the existing Ops progress channel
before dispatch. A supervised child using the existing detailed build
report emits this event without a child watchdog. The event can advance
the enclosing idle window once and carries neither compilation success
nor admission. The action and aggregate deadlines remain fixed. Use the
owner-mismatch control and the =CompilerProgress= replay counterexample
to verify this distinction.
