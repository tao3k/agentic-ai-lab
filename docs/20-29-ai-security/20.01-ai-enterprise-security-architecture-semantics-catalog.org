* Status

DRAFT — architecture-semantics discovery owner.

This document is non-normative.  It collects architecture semantics from
enterprise practice, standards, papers, incidents, blogs, and issue reports.
Normative Agentic AI Lab composition rules belong to
=20.02-composable-ai-security-architecture-package=.

* Decision

Agentic AI Lab does not adopt one external layer model as its own architecture.
Agentic AI Lab is the engine that composes architecture design semantics.

External three-layer, seven-layer, ten-layer, lifecycle, control-plane, and
threat-taxonomy models are evidence sources.  Their concepts are normalized
into reusable semantic objects and relations without erasing their original
ownership or claiming that differently named layers are equivalent.

The catalog therefore answers:

1. What semantic objects and relations does an architecture define?
2. Which security properties does it require?
3. Which lifecycle or runtime boundary consumes those properties?
4. What evidence supports the mapping?
5. Which semantics can be reused, specialized, replaced, or remain missing?

* Agentic AI Lab engine boundary

This catalog MUST NOT:

- redefine Agentic AI Lab as a control plane or a particular security architecture;
- add a new public module DSL or raw record/alist architecture DSL;
- widen the public =compose=, =profiles=, =use-module=, or =use-composition=
  surface;
- make external taxonomies semantic owners of Agentic AI Lab;
- collapse policy, observation, proof, runtime admission, and effects into one
  authority;
- treat an LLM-generated mapping as verified architecture evidence.

The existing POO-native and functional engine remains the owner of composition.
Architecture catalogs and packages are values composed by that engine.

* Discovery method

Each external source is processed through five distinct states:

#+begin_example
external observation
  -> candidate architecture semantic
  -> owner-reviewed mapping
  -> optional proof obligation
  -> optional runtime projection
#+end_example

An external observation is not a policy.  A candidate mapping is not a proof.
A proof is not runtime admission.  Runtime admission is not effect completion.

* Architecture coordinate kinds

External sources organize architecture in different coordinate systems.
The coordinate kind MUST be retained with the source.

| Coordinate | Meaning | Example |
|------------+---------+---------|
| layer | structural or dependency stratum | CSA ten-layer architecture |
| domain | responsibility or operational grouping | CSA three operational domains |
| stage | temporal transformation step | perceive, reason, act |
| service | deployable provider boundary | model, tool, knowledge service |
| plane | independently governed operational surface | data or control plane |
| overlay | concern applied across other coordinates | security, observability |
| lifecycle | state transition over time | design, deploy, monitor, recover |
| taxonomy | classification of threats or controls | OWASP Agentic Top 10 |
| feedback loop | observation-driven system evolution | ADR Explorer to Detector |

Two coordinates MUST NOT be declared equivalent merely because their labels
overlap.  For example, an AWS service layer and a CSA semantic layer may map
partially without sharing ownership or runtime behavior.

* Reusable semantic object families

The catalog currently recognizes the following candidate families.  They are
architecture semantics, not new public engine APIs.

** Enterprise and environment

- organization;
- business purpose;
- jurisdiction and residency domain;
- human principal and accountable sponsor;
- environment, host, workload, and deployment boundary;
- risk acceptance and approval authority.

** Data and knowledge

- resource and data identity;
- provenance and authoritative owner;
- classification and sensitivity;
- purpose, consent, retention, and residency constraint;
- derived data and inferred sensitive attribute;
- document, message, tool result, embedding, index, context, and memory;
- knowledge claim and confidence/evidence status;
- ingress, retrieval, transformation, persistence, and egress.

** Model and intelligence

- model/provider/artifact identity;
- model revision and routing decision;
- system instruction and prompt/context assembly;
- inference request and output;
- guardrail or evaluator;
- model capability and evaluation scope;
- nondeterminism, drift, fallback, and evidence ceiling.

** Agency and composition

- human, software, AI, and composite principal;
- agent identity and accountable owner;
- module/composition identity;
- profile and capability;
- delegation, subagent, collaboration, and continuation;
- intent, plan, action, and causal predecessor;
- tool identity and provider identity.

** Policy, authority, and admission

- policy identity and revision;
- obligation and exception;
- authority grant and capability confinement;
- evidence requirement;
- admission, denial, escalation, and approval;
- budget, generation, idempotency, and effect containment.

** Execution and effects

- tool invocation;
- effect claim;
- execution environment and isolation boundary;
- reversible and irreversible effect;
- effect completion and publication;
- compensation and rollback;
- external side-effect owner.

** Observation, response, and recovery

- non-authoritative telemetry;
- authoritative observation;
- =ObservationEvent=;
- anomaly or incident candidate;
- =RecoveryDecision=;
- retry, resume, defer, deny, compensate, and escalate;
- recovery authorization and causal continuity.

** Evidence, proof, and governance

- evidence root and provenance digest;
- source and artifact identity;
- theorem/property obligation;
- Lean discharge;
- =IndependentDeclarationBundle=;
- runtime accept gate;
- independent replay;
- proof coverage, unknown/escalation rate, and replay success;
- counterexample, policy refinement, regression receipt, and release revision.

* Cross-architecture mapping status

Every mapping MUST use one of these statuses:

| Status | Meaning |
|--------+---------|
| exact | identities and required relations coincide under an explicit proof |
| refinement | target adds stricter obligations while preserving source meaning |
| projection | target intentionally exposes a bounded subset |
| partial | only named objects or relations correspond |
| conflicting | obligations cannot both hold for the selected profile |
| unknown | evidence is insufficient; composition fails closed where required |

Names alone never establish =exact=.

* External observation and issue admission

Blogs, papers, benchmarks, advisories, and GitHub issues enter as immutable
external observation records.  A record SHOULD retain:

- source URL and retrieval identity;
- publication/update revision;
- source type and declared owner;
- affected products and versions;
- reported preconditions;
- claimed attack or failure;
- observed or emulated effect;
- reproduction status;
- architecture coordinates named by the source;
- candidate semantic objects and relations;
- confidence and unresolved contradictions;
- linked counterexample or test artifact;
- review decision and superseding observation.

This is a conceptual contract.  It MUST NOT become a raw public alist/YAML DSL.
Concrete representation requires a separate POO-native owner.

* Architecture discovery questions

For each new source:

1. Does it reveal a new semantic object, relation, invariant, or lifecycle?
2. Is the issue internal to one architecture coordinate or a boundary crossing?
3. Did identity, authority, provenance, evidence level, or restrictions change?
4. Which owner should have prevented, observed, or recovered the failure?
5. Is the source reporting production fact, emulation, benchmark, or guidance?
6. Can the case become a deterministic counterexample?
7. Can an obligation be discharged by Lean/property tests?
8. Which part remains semantic judgment or human risk acceptance?
9. What runtime receipt could demonstrate enforcement?
10. What new unknown/escalation population does the change create?

* Catalog governance

- New entries require a named external source or internal RFC owner.
- External sources remain immutable observations; corrections supersede them.
- Vendor product behavior is not generalized without an explicit mapping.
- A threat taxonomy cannot silently create runtime authority.
- A semantic mapping cannot silently create proof coverage.
- Unknown or conflicting mappings remain visible.
- Package implementations MUST preserve the parent/child repository ownership
  boundaries of their actual source owners.

* Acceptance criteria

- [X] Agentic AI Lab remains an architecture-semantics composition engine.
- [X] External layer models are evidence sources, not engine owners.
- [X] Coordinate kinds and mapping statuses are explicit.
- [X] Policy, proof, runtime admission, and effect completion stay separate.
- [X] Existing POO/profile boundaries are reused.
- [ ] Data/knowledge semantics have a POO-native package owner.
- [ ] Model/intelligence semantics have a POO-native package owner.
- [ ] Catalog observations have a versioned provenance representation.
- [ ] Cross-architecture mappings have proof/property validation.
- [ ] A runtime acceptance projection consumes composed architecture semantics.
